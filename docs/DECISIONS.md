## Session 2 — introduced-and-fixed-same-session

Logged for the audit trail, not because it shipped to anyone:

- Fixing #3 changed `classify_sentiment`'s return type for `return_probabilities=True` from a numpy array to a plain `list` (to match `TextProbResponse`'s declared `list[float]`). This broke `gui.py::update_radar_chart`, which called `.tolist()` on the result. Caught and fixed in the same session — `update_radar_chart` now does `np.asarray(probabilities)` on entry.

## Accepted for v1.0.0 (not bugs, deliberate scope)

- No auth, no rate limiting, no batching.
- Single hardcoded model version served (`0.2v`).
- No CI at all in v1.0.0 — a test workflow was drafted this session but deferred to v2.0.0 by decision.

## Deferred to 2.0.0 (breaking)

Findings #2 and #13 require the planned retrain on a fresh HF dataset with a fine-tuned transformer (DeBERTa/RoBERTa/ModernBERT candidate — see ROADMAP.md). #7 needs a decision on weight delivery (release asset / registry / manual step), not a retrain — carried into ROADMAP.md's new production-grade track rather than the model/data track.

## Sprint X1 / 2.0.0 data-track decisions (session 3)

Not bug findings — forward decisions for the 2.0.0 data pipeline, logged here for the same reason as the table above: decided once, not re-litigated.

| #   | Decision                                                                                                                                             | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 16  | Labelling via self-hosted **vLLM + DSPy**, not adoption of a pre-labeled public HF dataset                                                           | Surveyed candidate 3-class HF datasets are themselves either heuristic-labeled (Sentiment140-style, same problem as TextBlob) or already model-labeled (e.g. one candidate's labels come from `cardiffnlp/twitter-roberta-base-sentiment-latest`). Self-hosted, owned LLM-labelling is inspectable and swappable; an inherited pre-labeled set is not.                                                                        |
| 17  | v1.0.0's 3-class scheme (negative/neutral/positive) carries over unchanged into 2.0.0                                                                | No case made for restructuring; keeps model/API contract stable across the retrain.                                                                                                                                                                                                                                                                                                                                           |
| 18  | Storage: **MinIO** (raw landing) → **Postgres** (extracted text, `label` nullable) — not parquet-only                                                | Multi-source text accumulated across HF+Kaggle sources should be queryable for analysis later, not just consumed once at training time.                                                                                                                                                                                                                                                                                       |
| 19  | HF/Kaggle source-provided labels downloaded as part of each file but never read or used, at any pipeline stage                                       | Only raw text is wanted from these sources; label quality/provenance varies per source (see #16) and isn't trusted regardless.                                                                                                                                                                                                                                                                                                |
| 20  | Full migration to **UV** (`pyproject.toml`), dropping `setup.py`/`requirements.txt`/`dev-requirements.txt` entirely; Python floor 3.10 → 3.12        | No pip-compat retained — clean cut, single dependency source of truth (runtime/dev/train groups).                                                                                                                                                                                                                                                                                                                             |
| 21  | `pyproject.toml` dependency groups named `dev` and `train`; runtime deps live in base `[project.dependencies]`, no separate group                    | Simple, matches the existing `requirements.txt` (runtime) vs `dev-requirements.txt` (dev) split, with `train` newly carved out for training-only deps.                                                                                                                                                                                                                                                                        |
| 22  | MinIO bucket named `raw-data` (single bucket, source-prefixed keys — e.g. `raw-data/hf/sentiment140/...`, `raw-data/kaggle/tariqsays-1m-tweets/...`) | Avoids bucket-per-source sprawl; simple default, prefixes keep sources separable without extra bucket management.                                                                                                                                                                                                                                                                                                             |
| 23  | Postgres database named `contextlens`                                                                                                                | Relational store chosen (over staying parquet-only, see #18) because the extracted-text table needs `label` to be nullable and independently queryable/updatable in place as vLLM/DSPy labels rows — not a one-shot batch transform. Postgres is the team's existing default for structured local state; `contextlens` keeps the database name stable across `docker-compose.yml` and any client tooling that connects to it. |
Open questions arising from these decisions (not yet resolved) are tracked in `ROADMAP.md`'s "Not yet decided" list, not here.
